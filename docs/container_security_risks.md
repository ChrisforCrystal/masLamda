# 为什么 Docker (runc) 对 AI Agent 来说极其危险？

Master，这是一个非常**切中要害**的问题。

简单直接的回答：**是的，非常大。简直是"裸奔"。**

如果您的 AI Agent 只是跑自己写的受信代码，那没问题。
但如果您的 Agent 允许运行**用户上传的代码**或者 **LLM 生成的代码** (Python/Shell)，用 Docker (runc) 就是在玩火。

---

## 1. 核心原罪：共享内核 (Shared Kernel)

这是 Docker (以及所有标准容器) 最根本的架构缺陷。

- **Docker 的做法**: "即使我们住在不同的房间 (Namespace)，我们还是用同一个**接待员** (Host Kernel) 处理所有请求。"
- **黑客的做法**: "我不需要打破房间的墙，我只需要把**接待员** (Kernel) 搞定，我就拥有了整栋大楼的钥匙。"

### 攻击面 (Attack Surface)

Linux 内核有 **400+ 个系统调用 (Syscalls)**。
只要其中 **任何一个** 存在漏洞 (Bug)，攻击者就可以通过这一个漏洞，从容器里跳出来，直接控制宿主机。

> **比喻**: 您给了用户一把锁 (Namespace)，但他手里拿着螺丝刀 (Syscall)，他可以直接把门框卸了。

---

## 2. 真实案例 (恐怖故事)

### 💀 CVE-2019-5736 (runc 自身漏洞)

- **原理**: 恶意容器可以覆盖宿主机上的 `/usr/bin/runc` 二进制文件。
- **结果**: 当管理员在宿主机上执行 `docker exec` 时，实际上执行的是攻击者的代码。**一瞬间，宿主机 root 权限到手。**
- **影响**: 几乎所有当时的 Docker 版本都中招。

### 💀 Dirty COW (脏牛漏洞)

- **原理**: 利用 Linux 内核内存管理的竞争条件漏洞。
- **结果**: 容器内的普通用户可以直接修改宿主机的只读文件 (比如 `/etc/passwd`)。
- **影响**: 这是内核级漏洞，Docker 根本防不住，因为它和宿主机用的是同一个内核。

---

## 3. 为什么 AI Agent 场景更危险？

AI Agent 场景和其他 Web 服务场景不同：

1.  **代码不可信**: Agent 的核心功能就是 Execute Code (执行 LLM 生成的 Python)。LLM 可能会被 "提示注入" (Prompt Injection)，生成恶意代码。
2.  **环境复杂**: Python 的 `os`, `subprocess`, `ctypes` 等库赋予了代码极高的系统访问权限。
3.  **多租户**: 您可能在一个集群里跑成百上千个用户的 Agent。一旦一个被攻破，横向移动 (Lateral Movement) 非常容易。

---

## 5. 假如被黑了，他能干嘛？(The Kill Chain)

Master, 您问到了最恐怖的部分。一旦黑客通过容器逃逸拿到了宿主机的 Root 权限，他能做的远不止 "控制物理层" 这么简单。这是一个连锁反应：

### 1. 偷光你的家底 (Data Exfiltration)

- **偷模型**: 您的宿主机上可能正在运行其他高价值模型 (如 Llama-3 的微调权重)。黑客可以直接挂载宿主机磁盘，打包带走。
- **偷密钥**: 搜刮宿主机的 `/etc/`, `~/.ssh/`, 以及 K8S 的 `Secrets` (ServiceAccount Token)。
- **偷代码**: 如果您的代码也没加密放在磁盘上，直接被因特网开源。

### 2. 免费的矿机 (Cryptojacking)

- **挖矿**: AI 节点的 GPU 是最香的。黑客会部署挖矿脚本，占满您的 H100/A100 算力。您付电费，他赚钱。
- **DDoS 肉鸡**: 利用您的千兆带宽去攻击别人 (比如五角大楼)，最后警察上门抓的是您。

### 3. 集群大屠杀 (Lateral Movement)

- 这也最致命的一点。攻陷一个 Node = 攻陷整个 K8S 集群的入口。
- 他可以使用节点上的 `kubelet` 凭证，向 API Server 发送请求。
- 他可以列出集群所有 Pod，然后通过网络扫描攻击内网数据库、Redis、其他微服务。

### 4. 永久驻留 (Persistence)

- 他会在宿主机内核里装 Rootkit。
- 即使您删除了那个恶意的 Docker 容器，重启了服务器，**他还在那里**。只要机器一开机，他的后门就自动运行。

## 6. 我们的解决方案 (The Trinity)

这就是为什么我们要引入 gVisor 和 Kata：

| 技术                   | 解决方案                                                                              | 安全等级             |
| :--------------------- | :------------------------------------------------------------------------------------ | :------------------- |
| **Docker (runc)**      | ❌ 共享内核，依赖 Namespace 隔离，防君子不防小人。                                    | ⚠️ **极低**          |
| **gVisor**             | ✅ **拦截所有系统调用**。用户代码只能跟 gVisor 的假内核 (Sentry) 说话，碰不到真内核。 | 🛡️ **高**            |
| **Kata / Firecracker** | ✅ **硬件级虚拟化**。每一个 Pod 都是一台独立的虚拟机，有独立的内核。                  | 🧱 **极高 (天花板)** |

**结论**: 对于 AI Sandbox 来说，**runc 是不可接受的**。必须上 gVisor 或 VM 类沙箱。
