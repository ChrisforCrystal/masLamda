# 功能规范: 仪表盘 UI (Dashboard UI)

**特性分支**: `001-dashboard-ui`
**创建日期**: 2025-12-03
**状态**: 草稿
**输入**: 用户描述: "增加一个UI界面，允许我上传wasm，以及node节点，控制节点的观测"

## 用户场景与测试

### 用户故事 1 - 插件上传与管理 (优先级: P1)

作为一个开发者，我希望通过 Web 界面上传 Wasm 文件，而不是使用 curl 命令，这样更直观便捷。

**为什么优先级最高**: 提升易用性，降低使用门槛。

**独立测试**: 打开浏览器，访问 Dashboard，点击“上传”，选择 `.wasm` 文件，上传成功并显示执行结果。

**验收场景**:

1. **Given** 打开 Dashboard 首页, **When** 点击上传按钮并选择文件, **Then** 文件被发送到 Controller，并显示“上传成功”及执行结果。

### 用户故事 2 - 集群状态观测 (优先级: P1)

作为一个运维人员，我希望看到当前集群中有多少个 Runner 节点在线，以及 Controller 的状态，以便监控系统健康度。

**为什么优先级最高**: 了解系统运行状况的基础。

**独立测试**: 启动多个 Runner，刷新 Dashboard，应该能看到节点列表。

**验收场景**:

1. **Given** 系统中有 3 个 Runner 在运行, **When** 访问“节点状态”页面, **Then** 列表显示 3 个 Runner 的地址和健康状态。

## 需求

### 功能需求

- **FR-001**: `flash-controller` 必须提供 `/status` API，返回当前连接的 Runner 节点列表。
- **FR-002**: `flash-controller` 必须提供静态文件服务，用于托管前端页面。
- **FR-003**: 前端页面必须包含一个文件上传区域，支持拖拽上传 Wasm 文件。
- **FR-004**: 前端页面必须实时（或轮询）展示 Runner 节点的健康状态。

### 关键实体

- **ClusterStatus**: 包含 Controller 信息和 Runner 列表的数据结构。
- **RunnerInfo**: 单个 Runner 的元数据（地址、状态、最后心跳时间）。

## 成功标准

### 可衡量的结果

- **SC-001**: 用户可以在 3 次点击内完成 Wasm 文件的上传和执行。
- **SC-002**: 新启动一个 Runner 后，Dashboard 应在 5 秒内更新显示。
