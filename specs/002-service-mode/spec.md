# 功能规范: Wasm 服务模式 (Reactor)

**功能分支**: `002-service-mode`
**创建时间**: 2025-12-03
**状态**: 草稿
**输入**: 用户描述: "部署 Wasm 我就可以启动服务了"

## 用户场景与测试

### 用户故事 1 - 部署长运行服务 (优先级: P1)

作为一个开发者，我想部署一个 Wasm 模块作为持久化服务（例如 HTTP 服务器或消息消费者），这样我就可以构建微服务，而无需管理操作系统进程。

**优先级理由**: 实现真正的 Wasm 微服务架构，超越 FaaS 模式。

**独立测试**: 部署一个监听端口（或模拟循环）并随时间处理多个请求的 Wasm 模块。

**验收场景**:

1. **给定** 一个包含死循环或事件监听器的 Wasm 模块，**当** 部署时，**那么** 它应该无限期地继续运行。
2. **给定** 一个正在运行的 Wasm 服务，**当** 发送多个请求时，**那么** 它应该按顺序或并发处理它们，而不会重启。
3. **给定** 一个正在运行的服务，**当** 我发送“停止”命令时，**那么** 它应该优雅地终止。

### 用户故事 2 - 服务生命周期管理 (优先级: P2)

作为一个运维人员，我想通过 Controller 启动、停止和查询 Wasm 服务的状态。

**优先级理由**: 管理长运行进程所必需的。

**独立测试**: 使用 Controller API 列出正在运行的服务并杀死特定服务。

**验收场景**:

1. **给定** 一个已部署的服务，**当** 我查询 `/services` 时，**那么** 我应该看到它列出且状态为“运行中”。
2. **给定** 一个正在运行的服务，**当** 我调用 `/services/:id/stop` 时，**那么** 服务停止且状态变为“已停止”。

## 需求

### 功能需求

- **FR-001**: `flash-runner` 必须支持 "Reactor" 模式 (WASI Reactor)，即模块导出 `_start` 或初始化函数但保持存活。
- **FR-002**: `flash-runner` 必须支持异步执行，允许在同一线程/进程池上并发运行多个服务。
- **FR-003**: `flash-controller` 必须提供 `deploy` (启动) 和 `terminate` (停止) 长运行服务的 API。
- **FR-004**: 运行时必须支持 WASI Sockets（或宿主函数等效项），允许 Wasm 服务接受网络连接（MVP 阶段可选，可用宿主驱动循环模拟）。

### 关键实体

- **ServiceInstance**: Wasm 模块的一个运行实例。
- **ServiceID**: 运行服务的唯一标识符。
- **ServiceStatus**: 枚举 (启动中, 运行中, 已停止, 失败)。

## 成功标准

### 可衡量的结果

- **SC-001**: Wasm 服务可以运行 > 1 小时而不崩溃 (稳定性)。
- **SC-002**: 单个 Runner 可以托管 > 10 个并发 Wasm 服务 (密度)。
- **SC-003**: 服务启动时间 < 50ms。
